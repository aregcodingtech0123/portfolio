# Performance baseline, 2026-10-12

Written for: the site owner, deciding what to fix first and what budget to enforce afterwards.

No application code, styling, dependencies (beyond the Lighthouse dev dependencies) or configuration was changed to produce this. Tooling is in `scripts/perf/` (commit `fca730c`). Raw tables: [lighthouse-summary.md](baseline-2026-10-12/lighthouse-summary.md), [bundle.md](baseline-2026-10-12/bundle.md), [observe-summary.md](baseline-2026-10-12/observe-summary.md).

## 1. How this was built, served and forced (reproduce with `npm run perf`)

- **Build and serve:** `next build` then `next start -p 3200`, Next 16.2.6 / Turbopack, with the same env block as `playwright.config.ts` (empty Sanity ids so the fallback dataset is served, dummy EmailJS ids, Cloudflare's public Turnstile test keys), plus blank `GEMINI_API_KEY` and `SANITY_API_WRITE_TOKEN` so the real values in `.env` cannot load. Port 3200 so it does not collide with e2e (3100).
- **Browser:** Playwright's Chromium 156 build, headless, driven by Puppeteer for Lighthouse 13.5.0 (performance category only). Mobile uses Lighthouse's default profile (Moto G Power emulation, simulated Slow 4G: 150 ms RTT, 1.6 Mbps, 4x CPU). Desktop uses Lighthouse's desktop preset (10 Mbps, 40 ms, no CPU slowdown).
- **Forcing skin and mode:** the `?skin=`/`?mode=` overrides are compiled out of production, so a script registered with `Page.addScriptToEvaluateOnNewDocument` writes `skin` and `theme` into `localStorage` on the site origin before every navigation. It runs before the inline boot script, exactly like a returning visitor's saved choice. Lighthouse still clears storage and cache first, so each run is a cold first visit; the seed is applied at document creation, after that reset. After every run the harness reads `<html data-skin>` and the `dark`/`light` class back: **80 of 80 Lighthouse runs and 24 of 24 observer runs applied the requested combination.**
- **No real network:** Chromium starts with `--host-resolver-rules="MAP * ~NOTFOUND , EXCLUDE localhost"`, so any non-localhost host fails at the resolver. The only attempted external request was `challenges.cloudflare.com/turnstile/v0/api.js`, which failed as intended. (The e2e suite deliberately lets that one host through; this harness does not.) `next build` itself fetches Google Fonts unless cached; that is build time, not a measurement run.
- **Runs:** 5 Lighthouse runs per configuration (2 locales x 2 skins x 2 modes x 2 form factors = 16 configurations, 80 runs), interleaved round-robin so machine drift hits every configuration equally. Cells below are `median (min-max)`. A second tool (`perf:observe`) loads the page with *applied* CDP throttling and reads LCP candidates, layout-shift sources, long tasks and event timing from the browser (en only, 3 runs, 8 configurations). `perf:inspect` and `perf:bundle` produced the font, image, CSS, DOM and bundle numbers.
- **Guardrails:** lint, typecheck, 81 unit tests and 54 e2e tests all pass with the tooling added. Not wired into CI.

How far to trust it:

- **Mobile LCP, FCP, bytes and CLS are very stable** (LCP within about 1-2% in most configurations). **TBT is not**: spreads of 2-3x, and two single-run outliers (TBT 4477 ms, one observed-LCP of 3766 ms) that are machine hiccups. Read TBT only as "roughly 100-250 ms".

Turbopack prints no per-route size table, so first-load JS is read from the served HTML (`<script src>`), each chunk measured raw, gzip and brotli. Package attribution comes from `next experimental-analyze --output`, matching its chunks to the real ones by minified size (they agree within about 1%).

| route | HTML | first-load JS raw | gzip | brotli |

| not-found | 10.5 KB | 509 KB | 146 KB | 126 KB |

**Leak check, as asked:**

- **Sanity Studio: no.** `sanity`, `@sanity/ui`, `@sanity/vision`, `next-sanity`, `@sanity/client`, `@sanity/image-url` and `styled-components` are absent from every public client chunk. They exist only in the `/content-hub` route (5.9 MB raw), which public pages never request.
- **Gemini: no.** `@google/genai` is in neither the public nor the Studio client bundle. It is server-only behind `/api/translate`.
- **Sanity client code on the public site: none** in the browser; content is fetched in a Server Component.
- **Framer Motion** is used at five sites: `MotionConfig` in `[locale]/layout.tsx` (so it is in the shared chunk for every page), the mobile menu (`Navbar`), the project filter (`Projects`, uses the `layout` prop), the modal (`ProjectModal`) and the About terminal (`InteractiveTerminal`). Every use is a simple fade/slide.
- **Turnstile** wrapper is 6.1 KB raw and `Contact.tsx` is 11 KB raw, both in the first-load chunk. The Cloudflare script itself is a third-party request issued at about 300 ms (before any scroll). Its size could not be measured offline (blocked by design).
- **Everything is first-load.** All 13 chunks load in the initial HTML; nothing is lazy-split. Candidates and measured sizes: ProjectModal 7.4 KB raw, Contact 11 KB + Turnstile 6.1 + EmailJS 2.4 (about 20 KB raw), InteractiveTerminal 3.5 KB. Together about 30 KB raw, roughly 12 KB gzip, 5% of first-load JS.
- **Server Component candidates:** the 9 sections are client components only because they read `useSiteContent()`; they hold about 42 KB raw (13 KB gzip) of the JS and their content is also serialized into a 32 KB RSC payload inside the HTML.
- **Dead code:** `src/components/hero/NodeGraph.tsx` is imported nowhere, so it ships 0 bytes. Hygiene only.

## 4. Fonts, images, CSS and the rest

**Page weight (mobile, en, terminal, dark; identical in every configuration within 1 KB):** 891,534 B total = fonts 346,101 (8 files, 39%), scripts 250,760 (14), images 222,737 (2, **25%**), HTML 30,269, CSS 12,587, other 29,080 (a 25.9 KB `favicon.ico` plus small RSC fetches).

**Fonts (`next/font/google`, 4 families, all `display: swap`, all variable, latin + latin-ext each):**

| family | latin | latin-ext | both (preloaded) | used by |
|---|---|---|---|---|
| Inter (100-900) | 48.4 KB | 85.3 KB | 133.7 KB | both skins (body) |
| Bricolage Grotesque (200-800) | 41.2 KB | 18.7 KB | 59.9 KB | terminal headings |
| Source Serif 4 (200-900) | 51.0 KB | 42.0 KB | 93.0 KB | minimal headings |
| JetBrains Mono (100-800) | 40.5 KB | 15.2 KB | 55.7 KB | terminal mono |

- All 8 latin and latin-ext files are `<link rel="preload">`ed for every visitor: **342,356 B** in both skins and both locales. The skin is only known client-side (localStorage), so the server preloads all four families.
- By `FontFace.status`, terminal never uses Source Serif (**93.0 KB fetched, unused**). Minimal never uses Bricolage or JetBrains Mono (**115.7 KB fetched, unused**).
- latin-ext is pulled in for both locales (it is preloaded), so English visitors download 161 KB of latin-ext. I could not prove from `FontFace.status` that English text never touches it, and Turkish needs it (ğ ş İ Ğ Ş sit in U+0100-017F), so I am not recommending dropping it.
- Fonts do **not** block render (swap, and they are not in the critical request chain) and cause little layout shift (largest font-attributable shift 0.0006-0.003, from a 5-8 px navbar width change). Lighthouse's font-display check is clean.

**Images:**

| Project screenshots | Sanity `cdn.sanity.io` via `next/image` | n/a | n/a | n/a | **could not be measured**: the fallback dataset has no images and Sanity is unreachable by design. Also: `PortraitFrame` is mounted twice (one per skin) and each fires a `HEAD /images/profilephoto.jpeg` probe.

**CSS:** one stylesheet, 68,722 B raw / **12.0 KB gzip** (12.6 KB on the wire), render-blocking by design; Lighthouse's estimate is 80-150 ms on mobile. Both skins ship to everyone: the rules that target the minimal skin are 17.5 KB raw / **2.4 KB gzip** (about 20%), the terminal skin is the unscoped default. Coverage: 77-79% used on load, unchanged after a full scroll and opening a modal. No unused-CSS finding of substance.

**DOM:** 1,316 elements for every configuration. In the terminal skin 577 (44%) are inside `display: none` subtrees (about 100 KB of the serialized DOM); in minimal 846 (64%, about 130 KB). Each section renders both skins' markup and CSS hides one. This is the cost behind the 272-328 ms skin switch and part of the 228 KB HTML.

**HTML:** 228 KB raw, 30 KB gzip: about 199 KB markup (incl. 23.5 KB inline SVG), 32 KB RSC flight payload, i18n messages only about 5 KB.

**Main thread (mobile, 4x CPU):** script evaluation 470 ms, style/layout 352 ms, other 266 ms, parse/compile 57 ms. Long tasks per applied-throttling load: three, sum 510-600 ms, longest 291-361 ms, at about 0.9 s (first-chunk execution and hydration), about 3.7 s (the portrait mounting after its probe) and one other. CPU profile of the load: the Turbopack module runtime function alone takes 127-151 ms self time (module instantiation), react-dom about 200 ms. TBT (Lighthouse, simulated) is 117-189 ms median: the main thread is not the problem, the LCP chain is.

**Render-blocking / critical path:** the stylesheet only (12.6 KB gzip). Critical chain length is 81 ms locally. Layout shifts: worst CLS 0.017 (desktop minimal, the About grid re-laying out as fonts and the portrait land), everything else below 0.003. Layout shift is not an issue.

**Server:** `/[locale]` is built as dynamic (`ƒ`) and served with `Cache-Control: private, no-cache, no-store` even though `generateStaticParams` exists. Local TTFB is 13-20 ms with the fallback dataset. Probably caused by the root layout's `getLocale()` reading request headers; I did not verify that by changing code. With Sanity enabled each request would also hit Sanity (no `revalidate` is set); I could not measure either on a real host.

## 6. Surprises and what could not be measured

Surprises:

1. **Lighthouse says the LCP image is "discoverable in the initial document". It is not.** The server HTML contains no `/_next/image` URL; the hint is a false positive and I verified it against the HTML directly.
2. **React emits a preload for the About photo's 197 KB original** (an HTTP `Link` header) that is never used for the hero and is below the fold on mobile.
3. **The LCP element is not stable across runs or skins**: navbar logo, hero image or the About `h2`, depending on skin, viewport and a few percent of timing. On desktop terminal the hero is not even the LCP.
4. The 110 KB `polyfill-nomodule` chunk is in the HTML but is not downloaded by modern browsers; it inflates naive "first-load JS" counts by 12%.
5. The Studio and Gemini isolation is better than the brief feared: zero leakage.

Could not be measured, and why:

- **Turnstile script, iframe, and its main-thread cost, EmailJS:** third parties, blocked at the resolver by design. Only the request being issued at about 300 ms is known.
- **Sanity project screenshots** and any real content-driven image: the fallback dataset has none. If the live CMS has large screenshots they are untested.
- **Real hosting:** brotli transfer is computed (205 KB), not served; real TTFB, CDN caching and Sanity fetch latency are unknown. `/[locale]` being dynamic would matter there.
- **Real INP, real devices, field data:** none. The interaction numbers are scripted clicks on a fast desktop with 4x CPU throttling (BenchmarkIndex 2678), so they are a floor.
- **Fixes were not verified.** All "estimated gain" figures are derived, not measured on a patched build. The first post-fix `npm run perf` is the real test.
- **Observer coverage:** en only, 3 runs, 8 configurations; Lighthouse covered both locales with 5 runs. Playwright reports the two `HEAD` probe requests as failed while Lighthouse records them as 200; I did not resolve the discrepancy and did not rely on either.
- Bundle package attribution is the analyzer's per-module estimate (separate build, matched to the real chunks by size); per-package gzip overlaps and should be used for ranking, not summed.
